# 乐谱与健美操评分复核

2026-11-03，组织者在已有求解结束后复核。新增重复实验另行记录，不覆盖原结果。本目录的隐藏参考只用于事后检查，未提供给新求解会话。

## 结论与证据范围

发现并修复一项环境缺口：**用户Windows的正常代理没有传入WSL/Docker，导致Hugging Face等模型主机不可达。** 镜像原本启用了网络bridge，未注入离线开关，但不能据此声称已完整继承用户的网络通路。原乐谱11.16分虽可精确复算，也不能把工具受限完全归为模型能力不足。受影响的乐谱复跑R1已停止并记为环境中断，改用新编号R2在修复代理后重测。

未发现评分执行错误、错用参考文件、导出丢失音符或原MT3最终推理失败。**乐谱旧示例与本次采用不同评分版本，分数不能直接横比；健美操的官方评分本来就是严格整题 0/1。** 这并不证明所有转谱策略都正确，也不证明两次运行具有统计代表性。

## 网络环境缺口与修复

2026-11-03约23:23，针对新乐谱运行再次报告模型下载超时，做同URL对照：Windows经既有`127.0.0.1:7897`代理访问Hugging Face元数据HTTP200；容器没有代理变量、没有离线变量，直接访问返回`Network is unreachable`。这证实网络通路不同，不是模型自行拒绝联网。

通过仅监听WSL Docker网桥的本地SSH转发，让新容器使用用户已有Windows代理。新镜像`ale-two-tasks:20261103-userproxy`与原镜像的RootFS层、启动入口、用户和工作目录一致，只增加代理环境变量。新镜像内Hugging Face元数据HTTP200、YourMT3目录HTTP200、MT3权重Range请求HTTP206；这是实际容器验证，非仅检查“网络未关闭”。

证据：[缺口记录](network-proxy-defect.json)、[容器访问对照](proxy-connectivity-probes.jsonl)、[镜像层一致性](proxy-image-provenance.json)、[新镜像实际探测](proxy-image-probes.jsonl)。原独立v2成功运行了MT3，但YourMT3未下载成功，正常代理缺失是其工具可用性的实际限制，不能忽略。

`ale-music-nju-independent-repeat-r1`在组织者停止后为`status=failed, score=null`；官方终止确认触发保护，评分参考未暂存。它是环境中断，不是模型0分，不加入有效成绩或取最大值。`ale-music-nju-independent-proxy-repeat-r2`继续使用相同独立v2后缀、模型、强度和18000秒预算，新容器新上下文，不接收R1输出或审计提示。

健美操R1的来源审查确认全部作答素材为本地输入，未下载外部作答材料，其动作匹配失败仍保留；同时注明它使用未接Windows代理的直接bridge环境，不将其包装成代理修复后的实验。

修复后乐谱R2已实际下载YourMT3权重，**561,544,628字节**，SHA256 **`ae38e415c79efd5592dcb9b658cdb99ddb11d4c4e1eaa364cab04a052473fc25`**，与官方Hugging Face LFS记录一致。这明确区分“网络允许”“权重下载完成”和“推理成功”三个状态；推理与交付状态在R2结束后单独记录。证据：[官方模型摘要](yourmt3-r2-official-checkpoint.json)、[容器文件校验](yourmt3-r2-download-verification.json)。

## 乐谱：MT3 是否真正运行

- 最终权重为 183,672,643 字节，SHA256 `b8a3807ed265059abd25ad7f68142c06c35e8f6144dcaa45bd55946a3745398f`。文件完整且可严格加载全部参数。
- 通用工具来自 `openmirlab/mt3-infer` 的 `d8cbd287470291dee335f84315c5a9b9ff6e6c8a`。YourMT3 的下载没有成功，实际使用的是 MT3，二者不能混称。
- 中间确有依赖、Transformers T5 接口、预处理和 JSON 序列化错误；最终轨迹 `item_94` 在修复后正常退出。最终特征形状为 `(69, 256, 512)`，覆盖整段录音；输出 994 个候选音符事件。最长生成序列 354 token，未撞上 1024 的序列上限。
- Agent 随后做音色归属、谱面量化和过滤，最终只交出 378 次音符起音，另有 6 个全休止声部。MT3 成功运行不代表这条转写与过滤策略能够准确恢复复杂管弦乐。
- 对自定义 T5 缓存解码与独立的完整因果前缀解码做数值检查，16/16 步 argmax 相同，最大 logit 差 `3.0517578125e-05`。检查使用通用合成输入，Torch 2.2.2、Transformers 4.43.4；原运行 Torch 2.15.0，因此它仅支持缓存解码数学逻辑一致，不是对整套音频质量或原环境的等价证明。

证据：[解码检查](mt3-decoder-parity.json)、[检查脚本](../audit_mt3_decoder.py)、原独立运行 `origin_log/codex/run_mt3.py`、`mt3_events.json`、`score_events.json` 与 `transcript.jsonl`。

## 为什么旧乐谱示例更高

用户链接的旧案例记录为 Claude Opus 4.7 / OpenClaw，单次 **0.2220804767923586**；页面说明其交付是固定 32 小节模板，不是对完整录音的准确还原。旧任务代码为 `d10fb61a14f9719774c3520c5763068b28ef5546`，旧素材版本为 `d93bb510e472dcaa406f09fc800797268567ca5c`。录音与任务 brief 与当前输入摘要相同，但交付与计分协议已经变化：旧版主要基于 MIDI，当前还要求原生工程/MusicXML 的记谱匹配和导出一致性。

旧 `compute_dynamics_correlation` 在没有力度比较数据时直接返回 1.0。作为事后诊断，用旧音乐算法对当前冻结 MIDI 和当前参考计算，力度分可达 **0.9304607166**，音乐加权贡献 **0.2291834874**；现行算法的音乐贡献只有 **0.0115873405**。这说明旧算法会给稀疏或不匹配的音乐较高力度分，不能将旧示例的 0.2221 视为现行版本的合理分数下限。

该旧算法数值只是反事实诊断：**未恢复旧版全部参考与裁判环境，不能当作旧版完整官方成绩，不取代当前官方分数，也不在其上自行加排版分来报成绩。**

旧页面：[乐谱案例](https://wang-jiahao.github.io/omni-agent-cases/#ale-music)；网页数据快照 `legacy-casebook-data.json`；旧代码快照 `legacy-code/music-main.py`。

## 健美操：是否评分错误

旧页面 Gemini 3.1 Pro Preview / Gemini CLI 单次 1.0；页面没有可复核的该次完整轨迹或交付 XLSX，因此不能重新核验其作答来源或误差。新旧题目的视频和 FIG 规则摘要相同；旧版与当前的主任务、`verify_outputs.py` 在 CRLF 归一化后完全一致。

分别加载两个版本的官方 verifier：参考表自测均为 1，原提交均为 0，首个失败均为第 3 行 `ordered_match_failed`；只改参考中的一个 FIG code 也均为 0。原提交第 1、2、6、7 行与参考匹配，第 3、4、5、8 行不匹配。**4/8 只是事后逐行诊断，官方分数仍为 0，不另造部分分。**

评分器要求四列、8 行、总 credited_value 在 7.0–7.2，随后按顺序逐行核对 FIG_code 和 credited_value；任一不符就是 0，全部匹配才是 1。它不依据行匹配率给连续分，也不对动作名称和最低标准文字做完整语义判断。

证据：[新旧评分器对照与正负控制](aerobics-recheck.json)、[新旧代码摘要对照](version-comparison.json)；旧页面：[健美操案例](https://wang-jiahao.github.io/omni-agent-cases/#ale-aerobics)。

### 首差异动作的规则对照

参考第3行的动作名是 **FLAIR + AIR FLAIR**，提供的规则PDF第70页明确对应 **A319 / 0.9**。模型提交的 **A340 / 1.0** 则在第72页定义为背部转一周后，再腾空转体一周落俯撑的HELICOPTER。这不是同一个动作名称下单纯少给0.1。

原视频约28.8–29.3秒的保留抽帧可见竖直分腿、交替手撑的阶段，支持继续从动作类型与整段划分查找混淆；不能只凭前段背部旋转就把后面的完整动作归为HELICOPTER。此处仅做规则定义与画面对照，**不宣称完成了体操专家的技术复判，也不据此改写官方参考或分数**。未发现参考第3行的名称、代码和规定值彼此冲突。
