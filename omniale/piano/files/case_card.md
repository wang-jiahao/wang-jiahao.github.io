# OmniALE C1 案例：钢琴回课录音批改与反馈包（Brahms Op.118 No.2）· v3

- **case_id**：`omniale-c1-brahms-lesson-feedback`（v3）
- **分类**：C 分析与决策支持 → C1 专业分析、评审与反馈（演奏反馈）
- **能力标签**：
  - 音乐感知：复调音高、节奏、力度、声部平衡
  - 乐谱—录音对齐（录音中含重弹和卡顿）
  - 专业标准应用：区分错误与合理的音乐处理，对照谱面力度记号
  - 读谱：区分两遍乐句的差异
  - 跨材料关联：对照上周课后记录
  - 系统性归因
- **结构难度**：L2，多步骤综合工作
- **媒体**：音频（手机录制的钢琴、单声道 m4a，62.7 秒），辅以图片 PDF 乐谱和文本
- **环境**：E1 纯容器（只需 Python 和 ffmpeg），无需 GPU。乐谱只提供 PDF，不提供 MusicXML。

## 1. 设计动机：对 mmtb-piano 的诊断

在 MMTB 的 `piano-practice-feedback` 上，gpt-5.6-sol 的 F1 达到 0.8。那道题本质上是"把录音转成音符序列，再和乐谱做 diff"，而且录音是程序合成的：在量化 MIDI 上注入 5 处预设偏差。

| mmtb-piano 简单在哪里 | 本案例怎么做 |
|---|---|
| 机械量化的合成演奏，所以"偏离乐谱 = 错误" | 以职业钢琴家的真实表情演奏（MAESTRO/ASAP 的 Shilyaev03）为底稿，保留全部 rubato、句尾放慢和琶音。偏离乐谱不再等于错误 |
| 单声部，32 个音 | 双手复调，249 个谱面音符，含内声部和 3–4 音和弦 |
| 题目直接给出 200ms 时间阈值 | 不给阈值。赶拍、卡顿、节奏错误都必须相对于局部速度和平行乐句来判断 |
| 乐谱是一张简单的单行谱图 | 真实排版的钢琴谱 PDF（A 大调），涉及调号、小节内临时记号的延续和还原记号陷阱；两遍乐句大部分相同、局部不同 |
| 错音容差 ±1 半音 | 应奏和实奏 MIDI 必须完全正确。还包括八度错误，以及内声部的协和型错音 |
| 只看音高和时间 | 还考力度和声部平衡：必须读出谱面的 pp 并对照响度，还要判断旋律是否被伴奏盖住 |
| F1 ≥ 0.7 即通过 | 精确率和召回率都要 ≥ 0.75，且总分 ≥ 0.75 |
| 只有单一产物 | 交付完整反馈包：错误清单、两个系统性原因的归组、对上周记录逐条复查、证据片段、练习计划 |

## 2. 交给 Agent 的材料（`task/`）

- `TASK.md`：委托说明和交付格式。
- `materials/score.pdf`：第 1–16 小节的练习片段谱（用 verovio 从 ASAP 的 MusicXML 排版，在第 16 小节第 2 拍处截止）。
- `materials/recording.m4a`：学生的回课录音。合成方式是 UprightPianoKW 立式钢琴采样（CC0），再模拟手机录音：早期反射、带宽限制、轻度压缩、房间底噪和 50Hz 交流哼声，最后用 AAC 128k 编码。
- `materials/lesson_notes_week2.md`：上周课后记录，共 6 条。

### 3.2 中性位置（不计分）

第 3 小节第 1 拍和第 12 小节第 3 拍右手的 E4 是真实弹奏的（velocity 56/40），但被高八度的 E5 掩蔽，专业钢琴转录模型（ByteDance piano transcription）也测不到。人耳也未必能确认，所以模型报这两个位置漏音时，既不算命中也不算误报。

- **谱面要求的还原音**：
  - 左手第 4、12 小节的还原 G3。

- **弹得较轻但确实弹了的内声部**，例如：
  - 第 6 小节第 2 拍左手的 D#3（velocity 38）
  - 第 7 小节第 2 拍右手的 E4（velocity 46，重弹前后两遍都在）

### 3.5 媒体证据 → 关键决策 → 可验收结果

- 第 41–45s 的局部拍长比第 9–10 小节短 25–35%，而且这里是终止式；对照第 4 小节同样的终止是放慢的。→ 判断为失控的赶拍，不是 rubato。→ 报告 G18，上周第 5 条判 persists。
- 第 51.0–52.0s 卡住约 1 秒，位置在乐句中部、附点节奏之内；对照第 6 小节同一位置，那里没有停顿。而第 8 小节的长拍在句尾，属于合理呼吸。→ 只把前者报告为 G19。
- 谱面第 8 小节第 3 拍标 pp，第 9 小节是主题再现；录音中第 9 小节比第 1 小节响约 8 dB。→ 报告 G17。
- 第 1–2 小节旋律的估计力度只比伴奏高约 4（转录模型的 velocity 估计），而第 5–6、13–14 小节同类材料高约 20。→ 第 1–2 小节旋律没有被突出。→ 报告 G16（voicing）。
- 第 11 小节第 1 拍听到的是 E–G#–B 和弦，这是第 3 小节的和声；谱面第 11 小节是还原 F。→ 左右手各错一音，原因是照搬第一遍。→ 报告 G08/G09 并归入 P2。第 14 小节第 3 拍同理（G10）。
- 第 15 小节第 2 拍谱面没有升号，但同小节已出现 B#4，升号延续。→ 应奏是 72，录音弹的是 71。→ 报告 G04。
- 第 3 小节第 2 拍的和声听起来是升 c 小调，谱面是 A/C#。→ 内声部 A4 弹成了 G#4。→ 报告 G07。

## 4. 评分（`tests/verify.py`）

```
v3：total = 0.65·F1(问题检测) + 0.15·pattern 归组(P1、P2 平均) + 0.10·复查准确率 + 0.05·证据片段 + 0.05·练习计划
PASS = total ≥ 0.75 且 precision ≥ 0.75 且 recall ≥ 0.75
（v1/v2 的权重为 0.55 / 0.10 / 0.15 / 0.10 / 0.10，写在各版真值的 weights 字段里，verifier 按真值读取）
```

**v3 调整权重的理由**：v2 中复查、片段、计划这三项强模型几乎都能拿满，属于"认真完成交付"，不是专业判断。v3 把权重向问题检测和系统性归因倾斜。新权重只用于 v3，不回头重算 v1/v2。

- **音符级问题**（wrong_pitch / missed_note / extra_note / rhythm）：类型一致、小节一致、拍位误差 ≤ 0.5 拍、左右手一致、应奏和实奏 MIDI 完全一致，录音时间误差 ≤ 1.5s。
- **段落级问题**：
  - unsteady_tempo：小节范围覆盖第 11–12 小节且不超出第 10–13 小节，direction 为 rushing。
  - dynamics：范围覆盖第 8–9 小节中的至少一个，且不超出第 8–10 小节。
  - voicing：范围覆盖第 1–2 小节中的至少一个，且不超出第 0–3 小节。
- **hesitation**：位置落在第 14 小节第 3.5 拍到第 15 小节第 1.5 拍之间。
- **restart**：第 7 小节。
- **中性位置**：见 3.2，报告它们不计入命中，也不计入误报。
- **pattern 归组**：每个 pattern 的核心成员必须全部命中并共用同一个 pattern_id，这一组不能混入另一个 pattern 的核心成员（不能把两种原因混为一谈），并且要在 `patterns` 里有说明。组里多放几条相关问题不扣分（例如把第 14 小节 F#5 也归进"调号升号没落实"）。得分按 pattern 平均。
  - 规则由来：最初要求分组与真值完全一致，但 v3 实测发现模型做出了合理的更宽归纳，比如把临时升号延续也算作"变音记号没落实"，却被判失败。于是改成上面的规则，并对 v1–v3 全部提交统一重算（v1/v2 分数不变）。
- **证据片段**：用互相关把片段定位回原录音，相关系数需 ≥ 0.5，片段必须包含错误发生的时刻，时长 1.5–16s。
- **练习计划**：至少 3 条，并覆盖 3 个首要问题中的至少 2 个（P1、第 11–12 小节、第 7 小节）。
- **容错**：JSON 可以带 UTF-8 BOM。
- **自检**：
  - oracle（`solution/output/`）得分 1.00，20/20，P1、P2 都归组成功。
  - 可听性核验（`build/audibility_check.py`）：专业转录模型在渲染结果中测到了 99.2% 的真值弹奏音（测不到的 2 个已列为中性）；20 个问题中 10 个错音全部"测得到实奏音、测不到应奏音"；漏音位置全部测不到该音。

### 翻拍乐谱变体

Opus 的 0.98 依赖一条现实中不存在的捷径：解析矢量 PDF 自建读谱器。为此做了 `../brahms_lesson_feedback_scan/`：
只把 score.pdf 换成手机翻拍效果的栅格图（录音、真值、评分完全不变）。

| 模型 | 矢量 PDF 版 | 翻拍件版 | 变化 |
|---|---|---|---|
| claude-opus-5-5 | 0.981 ✅ | 0.902 ✅ | −0.079 |
| gpt-6-astra | 0.798 ❌ | 0.710 ❌ | −0.088 |
| claude-fable-5 | 0.558 ❌ | 0.663 ❌ | +0.105 |
| gpt-5.6-sol | 0.245 ❌ | 0.186 ❌ | −0.059 |

结论：降分有限，压不住强模型。Opus 换用了一条同样有效、而且真实可用的方法——把照片按小节高倍切片，
自动定位五线谱线，再叠加标注音高的参考线逐音读谱。说明**难度要加在判断层，不是输入形式上**。

Opus 5.5 几乎满分，关键在于它**解析了 PDF 的矢量图形**：按尺寸识别五线、符头和变音记号，再按坐标换算音高，相当于自建了一个精确的读谱器，所以第 11 小节拥挤的还原号也读对了。这条路径依赖乐谱是矢量 PDF；如果换成扫描件或手机照片，就不再可用，这是下一步最有原则的加难方向（见 results/ANALYSIS.md）。

- **v3**（20 项）：
  - 新增：
    - **第二个系统性原因 P2**：照搬平行乐句，3 个错音，跨左右手。
    - **voicing**：第 1–2 小节旋律被伴奏盖住。
  - 新增**可听性核验**：用专业转录模型逐音核验渲染结果，把测不到的真实音列为中性。
  - 评分权重向问题检测和系统性归因倾斜。
  - 为了避免"旋律弹轻"造成新的幽灵音，旋律力度设了下限（≥ 38），并通过转录核验确认每个旋律音都能被测到。
  - pattern 判定改为"核心成员同组、不混入其他原因"（见第 4 节），对所有版本统一重算。
  - 结论：v3 没有压低 astra 的总分（v2 为 0.79，v3 平均 0.78），但失败方式变了。召回率从 0.94 降到 0.80–0.85，误报从 6 条降到 3–6 条；第 11 小节还原号读谱 3/3 次失败；P2"照搬第一遍"0/3 次归组成功。
