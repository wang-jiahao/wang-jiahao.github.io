# RoomSound / A real spatial-audio scene explorer

Build a polished, useful web app for exploring this real 60-second room recording. The input is a synchronized 360-degree video and four-channel first-order Ambisonics audio from STARSS23 (SONY / Tampere University). This is a media-understanding AND web-implementation task. Recover audible events and their locations from the supplied evidence tools. Official annotations are not available to you.

The website itself must make sound, space, video, and time interactive. Do not replace it with a requirements summary or a conventional list of audio players. Do not claim isolated source playback: this is a mixed soundscape, without individual stems.

## Assets and perception

Immutable assets are `/media/scene.mp4` (silent 1920x960 equirectangular video), `/media/scene-foa.wav` (24kHz, PCM16, channels W,Y,Z,X), `/media/scene-mono.wav` (W channel), and `/media/scene-stereo.wav` (fixed yaw0 stereo preview). Video and all audio start together at task time0 and last60s. No autoplay. Use an explicit user gesture to start audio.

You can inspect exact video frames, real ASR, a general pretrained sound classifier's uncertain predictions, and raw signal-derived directional energy. These tools do NOT expose official labels. The gateway cannot accept native audio; this is explicitly a shared-perception-tools-assisted agent task. Cross-check evidence. Tools can misclassify, miss overlap, and confuse reverberation with sound direction.

## Product behavior

1. A panoramic viewport that can rotate horizontally through360 degrees using a yaw slider and dragging. Use an equirectangular crop with horizontal field of view120 degrees and vertical field of view90 degrees, centered at elevation0. This defined projection makes marker placement reproducible. The source panorama center is azimuth0; positive azimuth is LEFT, so source x=(180-azimuth)/360*1920. Panorama seams must wrap cleanly. Use a canvas or equivalent, not a static screenshot. Keep viewport aspect ratio4:3.
2. Actual audio must rotate with yaw. Implement the following simple horizontal FOA stereo decoder using the original four channels, not a panner on mono or the fixed stereo preview. For yaw a in radians, L=0.5*(W-X*sin(a)+Y*cos(a)); R=0.5*(W+X*sin(a)-Y*cos(a)). Z is unused in this horizontal decoder. Apply master volume after decoding. This is a simple stereo spatial preview, not an HRTF binaural simulation.
3. Play/pause, scrubbing, master volume, and a marked segment loop. Audio and video must stay aligned after seeking, pausing/resuming, changing yaw, and looping. Never play the mono/preview audio in parallel with the FOA decode. The slider uses the video clock. Start no audio before the user presses Play.
4. Discover audible events from the recording and create an event timeline. Use the ontology: speech, clapping, telephone, laughter, domestic, footsteps, door, music, instrument, water, bell, knock. Merge the dataset's two speech categories to `speech`; no demographic inference is required. Do not mark a visible actor or object as sounding just because it is visible. Represent simultaneous sound sources independently. At least include every event class you find evidence for; uncertain details should be acknowledged.
5. Show markers for currently audible events, at their current world direction. Markers follow the supplied trajectories, disappear outside their active interval, and hide outside the viewport. Clicking an event in the timeline pauses, seeks to the midpoint of its first interval, and recenters the viewport on that event. Filtering affects both timeline and markers, but must not pretend to separate the mixed audio.
6. A clear professional layout, a usable timeline, readable labels, responsive layout, source attribution, and an evidence note distinguishing observation from inference.

## Deliverables and stable interface

Work only inside your project. Use local HTML/CSS/JavaScript; no network/CDN dependencies. The server supplies immutable `/media/*` assets and serves your own project files. You may use native WebAudio and canvas. Submit `index.html`, implementation files, `events.json`, and `evidence.md`. Inspect and exercise your own running page before finishing.

`events.json` must be `{ "version":1, "events":[...] }`. Each event has:
`{ "id":"unique-id", "class":"speech", "source":"your-consistent-source-id", "start":1.2, "end":3.4, "trajectory":[{"time":1.2,"azimuth":-45,"elevation":8},{"time":3.4,"azimuth":-30,"elevation":8}] }`.
All times are clip-relative seconds. Use separate events for separated audible intervals. Coordinates are degrees, azimuth[-180,180], elevation[-90,90]. Interpolate direction linearly along the shortest azimuth arc; clamp to the closest trajectory endpoint outside its keyframe range. For stationary sources one keyframe is sufficient. Event activity is start<=t<end. Source IDs are your own stable IDs, not official actor numbers. Do not invent precision you cannot support in evidence.md.

Use these public DOM hooks; styling and surrounding structure are your choice:
- `[data-testid="scene-video"]`: the actual HTMLVideoElement, muted. It may be hidden if a canvas displays it.
- `[data-testid="viewport"]`: the visible4:3 panorama surface and marker container. Its bounding box is the exact viewing rectangle.
- `[data-testid="play"]`: toggles play/pause.
- `[data-testid="seek"]`: range input, seconds0..60, responds to input/change.
- `[data-testid="yaw"]`: range input, degrees-180..180; increasing turns LEFT, responds to input/change.
- `[data-testid="volume"]`: range input0..1, default0.8, responds to input/change.
- `[data-testid="loop-start"]`, `[data-testid="loop-end"]`: number inputs in seconds; `[data-testid="loop"]`: checkbox.
- `[data-testid="filter"]`: select, values `all` and ontology class names present.
- `[data-event-id="ID"][data-role="event"]`: clickable visible timeline entry for each event in events.json.
- `[data-event-id="ID"][data-role="marker"]`: visible marker centered at the projected source position when active and in-view. Its bounding-box center must match the source; put long text in an offset child if needed.

Projection: d=wrap(azimuth-yaw) into[-180,180); visible if abs(d)<60 and abs(elevation)<45. Marker x/width=0.5-d/120, y/height=0.5-elevation/90. Keep clipping and seam behavior consistent. Update immediately when paused and seeking/yaw-changing, not only while playing.

## Performer tracking and evidence review

A source ID now means a visually tracked PERFORMER, consistently across their audible activities. For example a person's speech, laughter, walking and interaction with a door or faucet belong to that same performer track. This is attribution to a performer, not a claim that a faucet and a mouth are the same physical sound emitter. Assign your own IDs. Track continuity across position changes, silence, and class changes; do not create a new performer merely because the sound class changed. No demographic labels. Sounds that no person produces, such as a loudspeaker, an appliance or room equipment, are attributed by the held-out annotation to ONE single non-tracked background agent, even when they come from different directions; group them that way rather than giving each background sound its own agent. Admit uncertain associations in evidence.md. Performance is evaluated with an optimal anonymous one-to-one mapping, never literal ID equality.

Add a performer select [data-testid="source-filter"] with all and every events.json source ID. It filters timeline entries and markers together, in conjunction with the class filter. It never separates or silences the mixed audio. Add a checkbox [data-testid="follow-source"], default off. With one performer selected and Follow enabled, yaw follows the active event trajectory, including seeking while paused, playing, and wrapping +/-180 degrees. If several activities for this performer overlap, use the earliest-starting active event; break ties by event id. During silence hold the last yaw. Class filtering does NOT change this follow target. Selecting all turns Follow off. Manual yaw-slider input or viewport dragging disables Follow immediately. Picking a performer does not change playback time. Keep actual stereo decoding aligned with the changing view.

Build evidence-review bookmarks, derived from the MEDIA and your event inference, not by guessing answers from the question wordings. The ten questions are listed below.
If you genuinely cannot recover an answer, put unresolved:true and a reason rather than inventing it. This is honest, but not a correct answer for scoring.

Deliver reviews.json: {"version":1,"reviews":[{"id":"q1","start":1.2,"end":2.3,"source_ids":["p1","p2"],"event_ids":["event-a","event-b"],"note":"time-stamped evidence and uncertainty"}, ...]}. The example numbers are not answers. Include all ten ids. A review uses existing event and source IDs; IDs in source_ids are unique. Render one clickable entry per review using [data-role="review"][data-review-id="q1"]. On click pause, seek to that review's midpoint, and face the first source_ids performer using its earliest-starting active referenced event at the midpoint (otherwise its nearest referenced event). Set the performer selector to that ID and disable Follow. Unresolved entries must show their reason and must not pretend to navigate to a fabricated answer.

## Ten evidence-review bookmarks


`reviews.json` carries ten entries, `q1` through `q10`. Each is derived from the MEDIA and your own event inference:

- `q1`: The first interval where two different performers laugh at the same time. Use the overlap itself, not the union.
- `q2`: The first interval where two different performers clap at the same time. Use the overlap itself.
- `q3`: The first interval where one performer laughs while that same performer is clapping. Use the overlap itself, referencing both events.
- `q4`: The longest single continuous speech interval in the clip. Bookmark that interval and reference that event.
- `q5`: The first interval during which at least five audible sources overlap. Use that interval, referencing every event audible throughout it.
- `q6`: The first interval where a bell overlaps laughter. Use the overlap itself.
- `q7`: The first interval where a bell overlaps speech from both of the other agents at the same time. Use the overlap itself.
- `q8`: The first interval where two different performers speak at the same time. Use the overlap itself.
- `q9`: The interval during which both of the clip's continuous, whole-clip background sounds are audible, referencing both of them.
- `q10`: The first speech interval that starts after the last clapping in the clip has ended.

All ten follow the same schema, the same honesty rule for `unresolved`, and the same click behaviour. Each review additionally carries a freshness flag described below.

### Revision workbench

Your submitted `events.json` is the starting annotation, not a frozen fact. The page must let a reviewer correct it. Every correction is a single atomic change: it is applied as one step, is undone by one undo, and updates markers, the timeline, both filter option lists, the Follow target and review freshness together. Partially updated views are a failure.

Additional public DOM hooks:

- `[data-testid="edit-target"]`: select. First option value `none`, then one option per event, option value exactly the event id. Selecting an event loads that event's current class, start and end into the three fields below.
- `[data-testid="edit-class"]`: select over the twelve ontology classes.
- `[data-testid="edit-start"]`, `[data-testid="edit-end"]`: number inputs in seconds.
- `[data-testid="edit-apply"]`: button. Applies the three fields to the event selected in `edit-target` as one atomic change.
- `[data-testid="edit-error"]`: its text is non-empty exactly when the most recent attempted change was rejected, and empty after a change that succeeded. A rejected change must leave the annotation state byte-identical.
- `[data-testid="undo"]`, `[data-testid="redo"]`: buttons carrying the `disabled` attribute exactly when the corresponding stack is empty. `undo` reverts the most recent change and makes it redoable. `redo` reapplies it. Any new change clears the redo stack.
- `[data-testid="export"]`: button. It writes the current annotation state as `{"version":1,"events":[...]}` into `[data-testid="export-output"]`, in that element's `value` if it is a form field and otherwise its text. The exported document must be valid, complete and immediately re-importable.
- `[data-testid="import-input"]`: textarea. `[data-testid="import-apply"]`: button. Together they replace the whole annotation state with a pasted document, after validation, as one atomic change.
- `[data-testid="reset"]`: button. Restores the annotation state you originally submitted, as one atomic change, and clears any stored edits.
- Marker dragging: a marker intercepts pointer input only while its own event is the one selected in `edit-target`. Every other marker stays inert, so dragging anywhere else in the viewport still rotates the view and still disables Follow. Dragging the selected event's marker moves that event's trajectory keyframe whose `time` is nearest to the current playback time, ties going to the earlier keyframe. The new azimuth and elevation are the inverse of the documented projection at the marker's released center: `azimuth=wrap(yaw+120*(0.5-x/width))` and `elevation=90*(0.5-y/height)`, where `x` and `y` are measured inside the viewport box and elevation is clamped to `[-90,90]`. This is one atomic change and it must not rotate the view.
- `[data-role="review"][data-review-id="qN"]` additionally carries `data-stale`. It is `"true"` exactly when, under the current annotation state, none of that review's referenced events overlaps the review's own `[start,end)` window; otherwise `"false"`. An `unresolved` review is always `"false"`. Freshness is recomputed after every change, undo and redo.
- Edits persist: after a page reload in the same browser, the reviewer's current annotation state is restored. `reset` restores and stores the originally submitted state.

A change must be rejected, with `edit-error` set and no state change, when: `end<=start`; `start<0` or `end>60`; a field is empty, non-numeric or not finite; the class is outside the ontology; or, for an import, the document is not an object with `version:1` and an `events` array of at most 600 entries whose every entry has a unique string `id`, an ontology `class`, a string `source`, finite `start<end` inside `[0,60]`, and a non-empty `trajectory` of `{time,azimuth,elevation}` with finite numbers, `azimuth` in `[-180,180]` and `elevation` in `[-90,90]`.

Nothing here lets a reviewer separate the mixed recording, and editing an annotation never changes what the audio plays.

## Annotation repair: create, delete and split

Reviewers must be able to repair the kinds of inference errors this task can produce: a missed event,
a false detection, and two activities incorrectly bridged into one long event. Importing a hand-edited
JSON document is not a substitute for these visible operations.

Keep every existing player and workbench requirement. Add the following visible controls:

- New-event fields: `[data-testid="new-id"]`, `[data-testid="new-source"]` (text inputs),
  `[data-testid="new-class"]` (select over the twelve ontology classes), `[data-testid="new-start"]`,
  `[data-testid="new-end"]`, `[data-testid="new-azimuth"]`, `[data-testid="new-elevation"]` (number inputs),
  and `[data-testid="event-create"]` (button). Create one event with exactly that id, source, class and
  interval, with one stationary trajectory keyframe at its start. A new source is allowed and must
  appear in performer/filter controls immediately. Reject duplicate/empty IDs, empty sources, invalid
  classes, empty/nonfinite numbers, invalid intervals, out-of-range directions and a 601st event.
- `[data-testid="event-delete"]` deletes the event selected in the existing `edit-target` control.
  It is allowed to delete the last event. With no selected event this button may be disabled.
- `[data-testid="split-time"]` is a number input; `[data-testid="event-split"]` splits the selected
  event at that time. The time must be finite and strictly inside that event's current interval.
  Keep the original ID for the left half. The right half ID is the original ID followed by
  `~split-N`, where N is the smallest positive integer whose complete ID is unused at commit time.
  Both halves retain class and source. They span `[start,cut)` and `[cut,end)` without gaps or overlap.
  Each half's trajectory contains its own two endpoint keyframes and every original keyframe strictly
  inside its interval. Derive endpoint directions by the prescribed shortest-arc interpolation and
  clamping. Sort keyframes by time and never emit duplicate keyframe times. Thus the two pieces
  preserve the original direction at every original time, including a ±180° seam.

Each operation is exactly one atomic, undoable change. Undo restores the exact preceding document;
redo restores the resulting document, including generated IDs. New operations clear redo. Rejected
operations set the existing edit-error and leave annotation, history and persisted data unchanged.
Successful operations clear that error. Update the timeline, markers, class and performer filters,
edit-target choices, Follow selection and review freshness from the same state. Preserve selected
IDs when they still exist; otherwise select none/all as applicable and disable Follow if its source
disappeared. Keep the existing freshness definition; do not rewrite reviews' event references on
split or delete. Persist successful changes across reload, including an empty annotation, and allow
the existing Reset action to recover the originally submitted annotation as one undoable change.

The events schema accepts zero through 600 entries. IDs and sources are nonempty strings; all trajectory
times are finite, in [0,60] and strictly increasing; 1–1000 keyframes per event. The input annotation may
be empty. No operation changes the recorded audio. Generated IDs, create/delete/split, valid-empty
imports, arbitrary source names and mixed operation sequences can be tested using valid supplied fixtures.
