# RoomSound 在做什么，历轮怎样加难

核对日期：2026-11-03。依据原始 Claude 对话、各轮 TASK/protocol、ROUND-2/ROUND-3 设计记录与冻结评分结果。以下把题目变化、评分变化和测试修复分别说明。

## 用日常语言解释这道题

给 Agent 一分钟真实房间的 360° 录像和四通道空间录音，让它做一个“可以转头看、转头听的声音地图”。它要先判断：几秒到几秒有什么声音、声音在哪个方向、哪些声音属于同一个人；再把结果放进网页，用户能转动视角、按人物和声音种类筛选、点击书签跳到证据片段。

最后交付还要能人工纠错：改事件类别和时间、拖动声音位置、撤销重做、导入导出。改一个标注后，画面标记、时间线、筛选、人物跟随和相关书签都要一致更新。

四通道是空间方向的编码，并不是四个人各有一条干净音轨。房间里说话、笑声、鼓掌、铃声、音乐和家用设备声会混在一起；把网页做出来与把声音判断对，是两件都要完成的事。当前各次实验没有原生音频输入，Agent 主要读语音转写、声音分类与方向估计等工具结果，并结合视频抽帧或自编信号分析，不能把成绩解释成模型直接听音的水平。

## 谁改了什么

| 阶段 | 主要执行者 | 实质变化与目的 | 当时 Sol 历史总分 |
|---|---|---|---:|
| R0 修正版基线 | 较早的 Codex 会话 | 从空项目制作全景声音播放器；同时修评分器，要求真实 FOA 波形正确，防止仅凭左右声道能量比例蒙混过关。后者是验收修复。 | 84.11 |
| R1 | 较早的 Codex 会话 | 不再只识别孤立声音，还要把同一人的不同活动关联起来；新增人物筛选、Follow 跟随，以及 6 道需要依据录音回答的定位书签。 | 82.32 |
| R2 | Claude 主导；Codex 另有测试审查 | 从只读播放器升级成标注修订工作台，新增编辑校验、拖位置、原子撤销重做、书签失效和导入导出；书签从 6 道增加到 10 道。难点是所有视图共享一份状态，连续修改和撤销后仍一致。 | 80.80 |
| R3 | Claude | 保留 R2 权重，换成声音重叠更多、带连续背景声的真实录音。主要增加事件分离、方向定位、人物关联与时间边界判断的难度。 | 70.09 |
| 接续审计与真实 CLI 补测 | 当前 Codex 会话 | 沿用 R3 功能要求和素材；修验收漏洞与环境，补跑真正 Codex CLI。没有再增加新的产品要求或换更难素材。 | 见 CLI 正式报告 |

这里的“Codex 会话”是造题与审查的执行者，不代表早期候选是在 Codex CLI 中作答。R0–R3 的上述历史成绩来自自定义 Responses API harness；当前补测才是真实 Codex CLI。原记录没有做过正式 Claude Code 候选实验，也没有在本次补测中恢复 Claude API。

## 工程加难有没有起作用

R1 让事件身份在不同活动之间保持一致，例如同一个人的说话和鼓掌要归到同一人物。书签也从“界面上有按钮”变成“能找到录音中满足条件的片段”。

R2 更像一个小型标注软件：一次拖动只算一个历史步骤；编辑后撤销要同时恢复各视图；引用过被修改事件的书签要变旧；非法导入不能污染现有状态。这是有状态的工程要求。Claude 用正确参考解和故意做坏的工作台校准：参考解确定性 98/98，故障版本在新增工作台分项丢了 5.48 分。

不过 Sol 在 R2 新增工作台拿到 18/18，实现合计 48/48。这说明这批预定工程要求未难住该次 Sol，不等于所有工程要求都不可能再加难。

## R3 的录音具体难在哪

| 统计 | R0–R2 旧片段 | R3 当前片段 |
|---|---:|---:|
| 片长 | 60 秒 | 60 秒 |
| 平均同时活跃的声音事件 | 1.32 | 3.33 |
| 最多同时活跃的声音事件 | 2 | 5 |
| 至少 3 个声音事件重叠的时间占比 | 0% | 77.8% |
| 事件段数 | 26 | 36 |
| 贯穿全片的背景声 | 0 类 | 2 类 |
| 金标方向逐帧抖动 | 3.5° | 0.9° |

平均和峰值是同时活跃的声音事件数，不是人数。新片段不仅更密，标注方向还更稳定；目的不是拿更乱的金标制造失分。Claude 扫描可取得音视频的数据集窗口，结合类别覆盖、重叠程度与标注稳定性选出该片段。素材从 `fold4_room15_mix008` 的 60–120 秒，换成 `fold4_room24_mix014` 的 50–110 秒。

这一步把历史 Sol 内容分从 31.30/50 降到 20.59/50，总分从 80.80 降到 70.09；实现分都是 48/48。主要困难确实落在混合录音的事件推断。

但 R3 并非所有条件逐字不变：十道问题随新场景重出，题面披露了无人产生的声音统一归入背景代理的标注约定，ASR 关闭了会把整段音乐混合录音判成无语音的 VAD 门控，测试也让整段持续事件的“非活跃时应隐藏”检查记作不适用。这些都须披露，不能宣称严格单变量因果实验。没有实现的动态出题方案不计入已完成加难。

## 权重确实变过，不能把所有降分都归于难度

总分一直是 100，但分项权重调整过。R1 已把部分基础播放器分配给新增功能，并在内容里加入人物 IDF1。R1→R2 的原设计记录明确列出重新分配：时序 F1 15→12、类别加方向 F1 15→12、分段覆盖 10→8、人物 IDF1 10→8；书签答案从实现的 3 分改为内容的 10 分；基础播放器 36→22、人物筛选与 Follow 6→5，新工作台 18 分，导航 3 与审查 2 不变。

因此，旧总报告“全程没有改权重”的概括不准确，本次已纠正。84.11→82.32→80.80→70.09 可展示迭代历史，但前半段不是同题同权重的性能曲线。R2→R3 才保持相同分项权重，且仍有上面明确披露的适配。

## 当前 Codex 接手后主要修了什么

1. 补严书签证据引用：声称“两人鼓掌”却只引用一个人的事件不能得分。另建内容评分 v2，保留权重和容差；参考解 10/10，三份旧结果复算不变。
2. 修本机无头浏览器音频后端：默认后端连独立正弦波探针都没有有效时钟和 PCM。改用 Chromium 测试输出流，让真实音频图正常运算；不改候选产品代码，没有进行物理扬声器听音验收。
3. 修不合理误扣：题目未要求“未选事件点 Apply 必须报错”，测试却强点禁用按钮，把 Sol 整组编辑 5 分扣光。driver-v3 删除该未规定样例，保留四类非法字段检查；统一回归后 Sol 从诊断初评 69.12 恢复为正式 74.12。历史原结果和失败记录保留。
4. 把用户要求的候选接入真正 Codex CLI，使用 NJU Link、xhigh、允许联网与正常代理。CLI 可运行 shell、看图、操作浏览器并进一步分析文件，不沿用旧自定义 harness 的回合、工具、帧数和截图次数上限。旧新结果的条件差异明确标注。

这些修正让测试更符合原题、结果更可信；不能当作新一轮功能加难。最新真实 CLI 结果为 Sol 74.12、Astra 73.05、Terra 57.52，均 xhigh、允许联网，实现 48/48。Astra 内容23.55、审查1.5，书签3/10，耗时40分08秒（含三次网关重连）。Sol 给足主观 2 分的上界为 74.62，所以原先“Sol 确定性分加 2 仍低于 70”的目标目前未达到，也没有为达标继续调权重。
